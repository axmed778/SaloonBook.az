## 1. Что такое SalonBook.az

Онлайн-запись для салонов красоты, барбершопов и мастеров в Азербайджане, по подписке.

- У салона есть своя ссылка `salonbook.az/{slug}`, которую он ставит в Instagram bio.
- Клиент выбирает услугу, мастера и время, вводит номер телефона. Запись занимает около 30 секунд, без регистрации и приложения.
- Владелец видит календарь. Мастера видят только свои записи. Клиенту автоматически уходят WhatsApp-напоминания.

**Позиционирование** (README): _«Let clients book themselves 24/7»_, _«Stop answering booking requests manually in WhatsApp»_. Это «booking tool, not CRM/SaaS platform», и продукт не приводит салонам новых клиентов.

**Фактический охват шире:** в коде уже есть CRM-заметки, аналитика, зарплаты, платежи по записям, отзывы, публичная карта салонов и финансовый модуль.

**Возраст и процесс:** проект ведёт один человек (в playbook: «Я автор SalonBook, Баку»). Первый коммит 2026-07-28, 108 коммитов, работа идёт через PR (последний — #50).

## 2. Бизнес-модель

| Тариф | Мастера | Филиалы | Цена/мес | Внутренний enum |
|---|---|---|---|---|
| Start | 2 | 1 | 15 AZN | `START` |
| Salon | 8 | 1 | 35 AZN | `BASIC` |
| Pro | безлимит | 3 (+15 AZN за доп. филиал в коде) | 70 AZN | `PRO` |

- Первые 14 дней бесплатно, без карты (`TRIAL_DAYS = 14`, триал идёт на `BASIC`).
- Бесплатного тарифа для клиентов нет. `Plan.FREE` — внутренний «пол» без прав: сюда аккаунт падает после конца триала или неоплаты.
- Оплата ручная: владелец платит вне системы, платформенный админ активирует тариф. Таблицы `Subscription` и `Payment` заготовлены под будущий платёжный провайдер.
- После конца оплаченного периода действует льготный период `GRACE_DAYS = 3`.
- Акция «первые 50 салонов»: цена фиксируется на 12 месяцев (не скидка, оплата помесячно).
- Платящих клиентов пока нет, идёт этап привлечения через Instagram DM. Для этого есть `docs/dm-playbook.md` (готовые ответы AZ и RU) и ежедневный AI-дайджест лидов.

## 3. Архитектура

| Слой | Технологии |
|---|---|
| Web | Next.js 15 (App Router), React 19, Tailwind 4. Монолит: публичные страницы, дашборд владельца, админка платформы, API-роуты |
| i18n | `next-intl`: az (без префикса в URL), ru, en. По 1926 строк на язык в `messages/` |
| PWA | serwist, web-push |
| Worker | Отдельный процесс `worker/` на BullMQ и Redis. Создание записи его не ждёт |
| БД | PostgreSQL (Neon) и Prisma 6. Тенант определяется по `salonId` |
| Хостинг | Railway (сервисы `web` и `worker`), Cloudflare R2 и Turnstile, Resend для email |
| Внешние API | WhatsApp Cloud API, Instagram API, Anthropic SDK (дайджест) |
| Проверки | Vitest, Playwright (мягкий гейт в CI), ESLint, `pnpm typecheck`, GitHub Actions |

### Ключевые механизмы

- **Защита от двойной записи:** exclusion-constraint в Postgres (`prisma/constraints.sql`, `btree_gist`). Две подтверждённые записи одного мастера не могут пересечься даже при гонке или логической ошибке. Применяется на каждом окружении через `pnpm db:constraints`.
- **Auth:**
  - Владелец и сотрудники: email и пароль (scrypt) и HMAC-подписанная cookie. Сессия проверяется по БД на каждый запрос (`src/lib/auth/session.ts`).
  - Клиенты: вход по телефону через OTP (WhatsApp, запасной вариант SMS через Twilio).
- **Публичная запись:** rate limiting в Redis, Cloudflare Turnstile, повторная проверка слота на сервере, окно записи вперёд не больше 60 дней.
- **Ссылка управления записью:** `/a/{token}`. Клиент может посмотреть, отменить или перенести запись без аккаунта. Токен перестаёт работать через 7 дней после визита.
- **Здоровье сервиса:** `GET /api/health` неглубокий (без БД и Redis), `?deep=1` проверяет и то и другое. Воркер пишет heartbeat.

### Что делает воркер

| Задача | Расписание |
|---|---|
| Уведомления WhatsApp (подтверждение, напоминание за 24 ч, отмена, алерты владельцу) | очередь `notifications` |
| Web Push владельцу и сотрудникам | очередь `push` |
| Проверка подписок (истёк ли триал или период) | ежедневно 03:30 Баку, плюс запуск при старте |
| Авто-закрытие записей CONFIRMED → COMPLETED через 48 ч | каждый час (`RECONCILE_INTERVAL_MS`) |
| Досылка зависших QUEUED-уведомлений | каждые 10 мин (`NOTIFICATION_SWEEP_INTERVAL_MS`) |
| Обновление Instagram-токена | 1-го числа месяца, 04:10 UTC |
| Дайджест Instagram Direct: Claude разбирает 30 дней переписок, затем WhatsApp основателю | ежедневно 09:50 Баку |

Частота таймеров подобрана так, чтобы не держать Neon (scale-to-zero) вечно бодрствующим.

## 4. Модель данных (`prisma/schema.prisma`, 883 строки)

- **Идентичность и тенанты:** `User`, `Membership` (роль и привязка к филиалу), `Account` (платящий бизнес, владеет `Subscription`), `Salon` (точка или филиал).
- **Каталог:** `Employee`, `Service` (категория для карты, аудитория MALE/FEMALE/ALL), `ServiceAddon`, `WorkingHour`, `TimeOff`.
- **Клиенты и записи:** `Customer`, `CustomerNote`, `Client`, `Appointment`, `AppointmentAddon`, `Review`.
- **Деньги:**
  - `AppointmentPayment` — оплаты, возвраты и чаевые по записи.
  - `Payout` — старая зарплатная модель.
  - `Payment` — оплата подписки SaaS.
  - `UsageCounter` — счётчик записей.
- **Уведомления:** `Notification`, `PushSubscription`, `WhatsAppSender` (свой номер, токен хранится зашифрованным AES-256-GCM).
- **Instagram:** `IgThread`, `IgMessage`, `IgToken`, `IgDigest`. Это не тенантные таблицы: один Instagram-аккаунт на весь деплой.
- **Служебное:** `AuditLog` (без `salonId`), `LegalConsent` (журнал согласий только на добавление), `Invite`, `PasswordResetToken`.

### Соглашения по данным

- Деньги хранятся целыми в qəpik, проценты в basis points (3750 = 37,5 %).
- Все `DateTime` — `timestamptz` в UTC, отображаются в Asia/Baku (UTC+4, без перехода на летнее время).
- Бизнес-даты хранятся строкой `"YYYY-MM-DD"` по Баку, через хелперы `src/lib/time.ts`. `Salon.timezone` в БД есть, но код его не читает: UTC+4 зашит жёстко.
- Люди в финансовых таблицах хранятся как `userId` без внешнего ключа плюс снимок имени, потому что отзыв логина удаляет строку `User`.
- Снимки цен и допов копируются в запись при бронировании (`priceMinor`, `AppointmentAddon`), чтобы правка прайса не переписывала историю.

### Названия, которые легко перепутать

| Имя | Что это |
|---|---|
| `Payment` | оплата подписки SaaS (не деньги за визит) |
| `AppointmentPayment` | деньги, принятые за визит |
| `Customer` | контакт конкретного салона (ключ: `salonId` и телефон) |
| `Client` | глобальная личность клиента по телефону, для OTP, истории и отзывов |
| «admin» в коде | платформенный админ (`User.isPlatformAdmin`), а не ресепшн |
| `ADMIN` (роль) | ресепшн салона |
| `STAFF` (в БД) | это MASTER в коде, переименовывать нельзя |

## 5. Роли и права

Роли: **OWNER**, **ADMIN** (ресепшн), **FINANCE**, **MASTER** (в БД `STAFF`). Плюс флаг платформенного админа.

- Весь код спрашивает **ключ права** (`requirePermission("payments.write")`, `requirePagePermission`, `requirePageAccess`, `accessRefusal`), а не имя роли. Таблицы прав живут только в `src/lib/auth/permissions.ts`.
- Проверок тарифа ровно две, обе в этом же файле: `roleOnPlan(role, plan)` (может ли роль существовать на тарифе) и `accessRefusal()`/`can()` (может ли роль это делать). Прямое чтение `featuresFor(plan).x` рядом с проверкой права запрещено, и `guard-coverage.test.ts` падает при нарушении.
- Логины: MASTER доступен со Start, ADMIN на любом платном тарифе, FINANCE только на Pro. Создаёт их только OWNER.
- Мастер видит только свои записи. Телефоны и деньги мастеру не отдаются: запрос их не выбирает, в сериализованной записи нет ключа `payments`.
- Чтение финансовых данных не привязано к тарифу: после понижения история остаётся видна, добавлять новое нельзя.
- Причины блокировки логина: `plan`, `branch` (филиал приостановлен), `inactive` и другие. Заблокированный логин остаётся без `salonId`, так что все проверки отказывают.

## 6. Изоляция тенантов

1. **Приложение:** каждый операционный запрос фильтруется по `salonId`. Это реальная защита почти всего продукта.
2. **RLS в Postgres:** страховка, чтобы забытый `where: { salonId }` дал ноль строк, а не утечку между салонами.

**Что RLS реально защищает сегодня:** только запросы через `withTenantScope` на клиенте `prismaRls`, то есть три места:
- `src/lib/booking.ts` (создание записи),
- экспорт клиентов в CSV,
- экспорт записей в CSV.

Всё остальное (около 136 запросов в дашборде, другие API-роуты, воркер, админка) идёт через owner-соединение без защиты на уровне БД.

**Как включается RLS:**
- Нужна роль `salonbook_app` без `BYPASSRLS`, создаётся только через SQL (консольные роли Neon получают `neon_superuser`).
- Дальше `pnpm db:rls` и `pnpm db:rls-grants`.
- `RLS_DATABASE_URL` задаётся только на web-сервисе, не на воркере.
- Откат: удалить `RLS_DATABASE_URL` и перезапустить.

`rls.sql` **применяется вручную** на Railway и Neon, деплой его не запускает. После каждой фазы, добавляющей таблицы, это шаг владельца. CI-тест (`pnpm test:rls`) падает, если появилась таблица с `salonId` без политики.

`Appointment` нельзя делать «строгой» без предварительной прокидки `salonId` через `getAvailableSlots` и `isSlotBookable`: пустой результат прочтётся как «слот свободен» и даст двойные записи.

**Принятые решения D1–D21 записаны в PLAN.md и обязательны.** Основные:
- Выручка и выплаты считаются по **дню записи**, смены по **дню платежа**.
- Чаевые не входят в выручку и в базу выплат.
- Один платёж не переводит запись в COMPLETED.
- Одна смена на день. Платёж после закрытия смены попадает в следующую открытую с пометкой «late payment».
- «Günü bağla» (сверка записей) предупреждает, но не блокирует закрытие смены.
- Старый payroll конвертируется в схемы `FIXED_PLUS_PERCENT`, а выплаты переезжают с Pro на Salon.
- Аренда кресла: клиент платит в кассу салона, в P&L учитывается только аренда.
- Округление: half away from zero, один раз на расчётный лист.
- Расходы доступны с тарифа Salon, отчёты и экспорты только на Pro. История остаётся читаемой после понижения.

   - одновременное аннулирование двух платежей одной записи может увести чистую сумму в минус;
   - страница удаления данных обещает больше, чем реально удаляется: суммы платежей остаются в `AuditLog`.
8. Нет `CLAUDE.md` и AGENTS-файла. Правила разбросаны по README и `PLAN.md`.
9. Нет импорта клиентов, нет депозитов, нет напоминаний вида «пора на коррекцию через N дней» (по playbook).

## 10. Рабочие правила репозитория

Из `PLAN.md`, README и комментариев в коде:

**Процесс**
- Одна фаза, одна ветка, один PR. После фазы запускаются `pnpm typecheck`, `pnpm lint`, `pnpm test` и пишется короткий отчёт.
- **Если код противоречит плану, остановиться и спросить.** Бизнес-правила не выдумывать.
- В конце каждой фазы обновляется `docs/finance/PLAN.md` (таблица статусов и раздел «As built»).

**Доступ**
- Авторизация только на сервере, только через `permissions.ts`.
- Проверка тарифа только в двух местах `permissions.ts`.
- Имена ролей нигде, кроме `permissions.ts`.

**База и деньги**
- Деньги в qəpik, проценты в basis points, бизнес-даты `YYYY-MM-DD` по Баку через `src/lib/time.ts`.
- Миграции аддитивные, повторно запускаемые, с откатом в заголовке. Значения enum добавляются через `ADD VALUE IF NOT EXISTS`. Constraints оформляются отдельными `ADD CONSTRAINT`.
- Новая таблица с `salonId` получает политику в `prisma/security/rls.sql` и запись в фикстуре RLS-теста в том же PR.

**Интерфейс и тесты**
- Каждая новая строка UI на az, ru и en, число ключей должно совпадать.
- Клиентский компонент, использующий namespace i18n, требует, чтобы этот namespace был в allowlist `CLIENT_NAMESPACES` в `src/app/[locale]/layout.tsx`, иначе пользователь увидит сырые ключи (проверяет `client-namespaces.test.ts`).
- Поверхность не должна хардкодить `payments: true`: флаг берётся из `canSeePayments(session)`.
- Тесты Vitest лежат рядом с кодом и в основном чистые. RLS-тест опционален и работает на реальном Postgres.

**Не трогать без явной задачи**
- Значение `STAFF` в БД.
- Exclusion-constraint против пересечений записей.
- `withTenantScope` и заданный им `set_config(..., true)`.
- Порядок параметров WhatsApp-шаблонов в `buildComponents` (менять только вместе с `docs/whatsapp-templates.md` и повторной отправкой шаблонов в Meta).
- Цены, тарифы и тексты `dm-playbook.md`, если задача этого не касается.

## 11. Запуск и окружение

```bash
pnpm install                 # плюс prisma generate
cp .env.example .env         # минимум DATABASE_URL и REDIS_URL
pnpm db:migrate              # миграции
pnpm db:constraints          # ОБЯЗАТЕЛЬНО: btree_gist и защита от двойной записи
pnpm db:seed                 # демо-салон demostudio
pnpm dev                     # http://localhost:3000
pnpm worker                  # воркер, отдельный терминал
```

- Node 20+, pnpm 9.15, Postgres, Redis. Есть `pnpm db:up` (встроенный Postgres для разработки).
- Деплой на Railway: `web` (предварительная команда `pnpm db:setup`) и `worker`.
- **На Neon два URL:** `DATABASE_URL` — pooled (с `-pooler`, параметры `pgbouncer=true&connection_limit=5`), `DIRECT_URL` — прямой, только для миграций.
- В продакшене приложение не стартует без `SESSION_SECRET` и реального `WHATSAPP_VERIFY_TOKEN`. Для проверки подписи вебхуков нужен `WHATSAPP_APP_SECRET`.
- Без `WHATSAPP_TOKEN` воркер только логирует отправки, при этом они отмечаются как SENT.
- Без Redis публичная запись продолжает работать (rate limit «fail open», постановка в очередь по возможности).

## 13. Как составить большой промпт

1. **Дайте главный источник правды.** Для финансов это `docs/finance/PLAN.md`. Для остального нужно решить, что считать каноном, потому что README местами устарел.
2. **Разбейте работу на фазы** по образцу PLAN.md: одна фаза, одна ветка, один PR, критерии «готово» (typecheck, lint, тесты, ключи локалей синхронны).
3. **Явно разрешите или запретите задавать вопросы.** По умолчанию в проекте принято останавливаться на противоречии.
4. **Перечислите зоны, которые нельзя менять** (раздел 10).
5. **Укажите порядок и зависимости фаз.** Например, фаза 3 (смена) читает те же `dayTotalsByMethod` и revenue-функции, что и фаза 2.
6. **Отделите шаги владельца от шагов агента.** Запуск `pnpm db:rls` на Railway и Neon, создание роли `salonbook_app`, отправка шаблонов в Meta, проверка на боевой БД делает человек.
7. **Скажите, что делать с известным долгом** (раздел 9): чинить по ходу или только фиксировать в документе.
8. **Задайте формат отчёта после каждой фазы:** что сделано, что изменилось относительно плана (раздел «As built»), результаты проверок, открытые вопросы.
